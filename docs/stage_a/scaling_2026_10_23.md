## Matched positions

The full eleven-round scenario is advanced by the unchanged scripted baseline to
Japan's actual Combat Movement menu. Declaration offers are legally resolved
before selecting that menu. Cases target rounds one, three and six. Matching
prepared-state hashes are required for comparisons between search budgets.

Searches repeat on the same roots without applying their selected actions;
serialized game state and execution RNG remain unchanged. Each case measures
three waves: one first-use wave and two waves with warm source-feature caches.
Search trees are fresh for each wave. All legal actions and rule/state fields
remain available. The depth settings are caps, not measured lookahead depths.

| Opening Japan search: simulations / depth cap | Mean warm batch time, four roots | Aggregate searched decisions/second | Sampled peak RSS |
| --- | ---: | ---: | ---: |
| 4 / 8 | 2.48 s | 1.614 | 1.14 GB |
| 16 / 16 | 10.46 s | 0.383 | 1.70 GB |
| 64 / 32 | 35.25 s | 0.113 | 2.58 GB |

These roots have 316–321 legal choices, including naval movement, loading and
raider designation. A searched decision here is one complete search query on a
fixed position; it is not an executed move or an added training row. Batch time
is the latency for all four concurrent queries; throughput divides completed
queries by search wall time, excluding startup and scripted preparation.

At 16 simulations, six roots and four tensor threads provide 0.383 searched
decisions/second, essentially the same throughput as four roots. Four roots with
six tensor threads also provide 0.382. Neither use of the full conservative
12-thread allowance improves on four roots and four tensor threads, whose count
is ten including both coordinators. Larger root batches take longer. The round-three menus contain
124–193 choices and produce
0.381 decisions/second with two roots at 16 simulations and 0.112 at 64. A
round-six root has 179 choices and produces 0.330 decisions/second at 16
simulations. Different root counts and positions prevent attributing these
differences to calendar age alone.

The larger model has width 64, two message-passing layers and 16,384 token
buckets, versus 16, one and 2,048 in the pilot. Its search case uses the same
prepared positions but different policy weights, so that case alone does not
isolate the computational effect of model architecture.

## Measured cost and next work

The [matched-position diagnostic](position_profile_2026_10_23.json) verifies the
first timing root's exact state and pilot model hashes. On its 316-action menu,
median operation wall times are:

| Operation, one root | Pilot model | Larger model |
| --- | ---: | ---: |
| Clone | 0.085 ms | 0.086 ms |
| Legal menu | 25.56 ms | 24.96 ms |
| Observation | 56.78 ms | 53.61 ms |
| One cloned rule transition | 53.17 ms | 52.57 ms |
| Evaluator, one-request batch | 77.68 ms | 103.32 ms |

These timings overlap in meaning and must not be added: the evaluator includes
observation/input construction and graph encoding as well as neural operations.
The rule transition includes the adapter's menu validation and the engine's
application. The operation profile runs on clones and preserves the actual state
and execution RNG. Both model sets and the source checkpoint remain unchanged.

Code inspection matches the timings: the adapter rebuilds a scheduled legal
menu while producing an observation that already contains a raw legal menu;
action application validates a menu before the engine validates the action
again. The next performance work should reuse legal menus and observation data
for unchanged states, with strict invalidation after actions and declaration
offers, and reduce repeated observation-graph construction. It must preserve
every legal choice, field and exact replay behavior. Increasing parallel games
or tensor threads did not improve measured throughput, so merely raising those
counts is not the next step.

A separate serial 16-simulation trace on this root visits one decision step in
15 simulations and two in one simulation; all leaves use the evaluator. The
configured depth cap of 16 therefore does not mean 16-step lookahead was
achieved. Its raw cProfile output identifies graph construction as a Python
hotspot, but records only 1.21 seconds of self-time against 3.10 seconds of wall
time. The report flags that accounting as partial. It is not used to assign
percentages of total search cost; the independent operation wall timers above
are the basis for the optimization recommendation.

After that performance pass, rerun these matched cases and complete a bounded
16-simulation episode batch before expanding multi-seed learning. The original
learning experiment remains evidence of improved completion/value prediction,

## Reproduction and interpretation

Raw outputs stay in the ignored directory
`studies/campaign/runs/scaling-2026-10-23-rcl014/`. The curated JSON report records
case configurations, model/source hashes, timing buckets, root progress, guards
and raw-output hashes: [all cases](scaling_2026_10_23.json). The benchmark CLI
preserves existing output files.

```sh
./.venv/bin/python -m studies.campaign.scaling_benchmark \
  --output studies/campaign/runs/NEW-RUN/japan-s16-d16.json \
  --checkpoint-weights studies/campaign/runs/stage-a-speedcheck-2026-10-23/checkpoint.pt \
  --full-campaign --start-round 1 --start-nation-index 2 \
  --start-phase combat_movement --start-decision-kind combat_movement \
  --roots 4 --threads 4 --cpu-budget 12 --memory-bytes 30000000000 \
  --simulations 16 --max-depth 16 --waves 3 --seconds 150
```

An episode case uses `--mode episode`, omits the starting-position filters, and
sets `--calendar-rounds 1` or `2`, or `--full-campaign`. Its transition limit is
separate from the real game horizon. Guarded reports retain the last saved root
progress and pending wave; completed-wave throughput excludes unfinished search
work, while watchdog time includes that work.

The portable diagnostic can be rerun on the same position:

```sh
./.venv/bin/python tools/profile_campaign_position.py \
  --output-dir studies/campaign/runs/NEW-RUN/profile-position \
  --checkpoint-weights studies/campaign/runs/stage-a-speedcheck-2026-10-23/checkpoint.pt \
  --matched-report studies/campaign/runs/scaling-2026-10-23-rcl014/japan-r1-s16-d16.json \
  --seconds 90
```

All timings come from one machine and one invocation per configuration. Warm
fixed-position queries are not a representative distribution of self-play
positions. The collection games provide complementary execution evidence, not
confidence intervals for playing strength. This tool does not launch learning
updates or a continuing training job.
