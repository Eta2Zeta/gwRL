# Units and facilities in slot maps — 16 November 2026

The position now keeps its units and facilities in `SlotMap`s instead of
`std::map`s keyed by name ([slots](../../engine/names.md#units-and-facilities-slots)).
Each unit and facility has a slot; the map finds a thing by name through a hash
table of slots, lists its things in name order, and keeps them in a deque, so
copying a position allocates a few blocks of units instead of a node per unit.
Nothing refers to a unit by its slot yet. Play is the same at every step of 300
random games and 4 searched games. The
[evidence file](slot_maps_2026_11_16.json) holds the exact values.

## Setup

As for the earlier changes on this page's day
([facility types](facility_type_numbers_2026_11_16.md) and the records it
links): `tools/compare_engine_builds.py`, random games with seeds 7000 to 7299
in four processes, and searched games with seeds 41 to 44 (64 simulations a
decision, depth 16, networks with random first-layer tables, one position at a
time). Records were compared with `9519ea7` for the same play and with the
facility types change (`1b620d3`) for the saving.

## The same play

- **Random games:** the same legal moves, chosen moves and positions at all
  443,974 steps of the 300 games, compared with `9519ea7`.
- **Searched games:** the same 4,985 events and final positions in all 4 games.
- **Iterating while things enter or leave:** a `SlotMap`'s iterators are places
  in name order, which an entering or leaving thing moves, where a `std::map`'s
  iterators stayed on their element. A build with `GWRL_CHECK_SLOT_MAPS`
  defined throws when an iterator is used after its map changed; the C++
  suites and the same 300 random games ran on it without one, with the same
  play.

## What it saves

| Workload | Facility types as numbers | Units and facilities in slot maps too | Change |
| --- | ---: | ---: | ---: |
| Random games: instructions to list the moves, per call | 6.08 M | 5.74 M | −5.6% |
| Random games: instructions to play a move, per call | 3.18 M | 3.02 M | −5.0% |
| Random games: instructions to roll the dice, per call | 2.54 M | 2.41 M | −5.1% |
| Four searched games: instructions | 5,334 G | 5,164 G | −3.2% |

Against the engine before any of these changes (`9519ea7`), listing the moves
now runs 42.8% fewer instructions (10.03 M to 5.74 M), playing a move 29.9%
fewer and a searched game 23.9% fewer (6,782 G to 5,164 G). Every kind of
engine call ran fewer instructions: finding a unit or facility by name compares
one name or two instead of the seven or eight of a search in name order, and
copying a position, which many checks do (the copy took 6.2% of the engine's
samples in a profile of the facility types build), no longer allocates a node
per unit.

To compare CPU time under the same load, the facility types build's searched
games ran between two runs of this change, back to back, after the Python test
suite had finished: the facility types build took 428.6 s, this change 424.1 s
and 416.1 s, 2.0% less. Their instruction counts were 5,321 G for the facility
types build and 5,169 G and 5,166 G for this change. The load average of the
Mac's other work was about 10, so the CPU times are rough; the instruction
counts are not.

## A first version was slower

The first `SlotMap` found a thing by name with a binary search over its slots
sorted by name. It played identically but listed a position's moves with 6.7%
more instructions than the facility types build (6.08 M to 6.49 M per call),
while playing a move took 1.3% fewer and rolling dice 3.1% fewer. A profile of
a searched game put 9.4% of the engine's samples in that search for units and
2.1% for facilities: each lookup compared seven or eight names through two
indirections, where the `std::map` it replaced compared as many names but
inlined its search into the rules. The hash table finds a name with one or two
comparisons.

## What this does and does not show

- **Measured:** identical play in 300 random and 4 searched games, also on the
  checked build; the instructions each engine call and each searched game ran;
  the CPU time of the searched games in a bracketed trio.
- **Not measured:** decisions per hour in a training batch.
- **Not done yet:** rules still name units and facilities everywhere, so each
  reference is a lookup by name; holding a unit's carrier and cargo, and other
  references, as slots comes next.
